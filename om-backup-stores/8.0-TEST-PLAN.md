that the **load-bearing safety net** (PR #770 snapshot-block validation +
PR #754 restoration-mode UI/API guardrails + PR #752 retry/recovery) made
it intact through the v8.0 backport. The 3 backing-store rollback shapes
are tested by the agent-side cv-polling path, the OM-side restoration-mode
state machine, and the daemon-side block-fileId pre-check — all of which
landed in PR #862.

#### Re-run note for Probe 3

The Run-1 attempt at Probe 3 exercised the wrong code path because the test scenario stacked two rollbacks (appdb + s3-meta), and the appdb rollback wiped `backupjobs.jobs.lastOplogPush` for poRepSet. The PIT picker correctly refused with `"Are you sure your backups were running…"` from `BackupSvc.checkLastOplogAfterPIT` — well before `SnapshotBlockValidationSvc` was reached. To properly test the PR #770 PITR-from-RS validator on v8.0:

1. **Reset:** ensure both appdb-rs and s3-meta-rs are at HEAD (no rollbacks active), poRepSet backup status has `lastOplogPush` populated and current.
2. **Take fresh snapshots:** at least 2 poRepSet snapshots, spaced ~5 min apart.
3. **Roll back ONLY `s3-meta-rs`** to a target between snapshot A and snapshot B. Leave appdb-rs alone.
4. **Attempt PITR** to a time between snapshot B and "now". Auto-picked starter will be snapshot B (broken). With `lastOplogPush` still current, the picker passes `checkLastOplogAfterPIT` and reaches the snapshot-block validator. **Expected:** `SnapshotBlocksMissingException` thrown with the "Snapshot X is no longer restorable…" message.

#### Run 1 cleanup — findings that are NOT v8.0 backport drift

Two observations from Run 1 were initially logged as suspected backport regressions; closer inspection of the code shows both are inherited from main (or below) and apply identically:

1. **`INVALID_AUTOMATION_CONFIG` on Probe 2 (UI path):** `SnapshotBlocksMissingException` extends `ValidationException`, whose default error code is `INVALID_AUTOMATION_CONFIG`. The dedicated `SNAPSHOT_BLOCKS_MISSING` code (HTTP 409) only fires on the public REST API endpoint (`/api/public/v1.0/groups/.../restoreJobs`) where `ApiCreateRestoreJobsSvc.java` catches the typed exception and re-throws with the specific code. The UI uses `/automation/restore/{groupId}` (`AutomatedBackupRestoreResource.createCMRestore`) which has no such catch — the default code surfaces. This is identical on main. **Closed: not a regression.**

2. **Picker masking on Probe 3:** As described above, the appdb rollback in our test scenario nuked `lastOplogPush`, which the picker correctly refuses. The snapshot-block validator never gets a chance to run. **Not a regression** — it's our test scenario hitting an earlier (and correctly-functioning) gate. Re-run Probe 3 per the procedure above to actually exercise the PR #770 PITR-from-RS path.

#### Potential follow-up (NOT a launch blocker)

**FU — PITR-from-RS auto-fallback to older clean starter.** When the most-recent-at-or-before-target snapshot has missing blocks AND an older snapshot in the PITR window is clean, the picker today rejects the whole request rather than walking back to the older clean candidate (replay covers the gap from oplog slices, which the s3-meta rollback didn't touch). Workaround documented in `RESTORE-FINDINGS.md` Scenario 2 Run 2 Probe 3: manually delete the broken `backupjobs.snapshots` doc, retry → picker falls back. This is a UX improvement worth filing for a future iteration, applies to main as well as v8.0.

#### Run 1 operational notes (gotchas for future runs)

1. **`OM_DONT_RUN_MIGRATIONS=1` is required to start v8.0 OM against a main-built appdb.** The migration framework refuses cross-branch `NoMigrationPathException` because the recorded last-application-version hash (main-era `875e8d9f7ef…`) isn't in v8.0's compiled-in migration list. The env var skips the migration runner entirely — safe here because main's migrations are a strict superset of v8.0's. JVM flag `-Dmms.migration.path.verify=false` did **not** work — the migration runner is invoked as a separate pre-step and doesn't pick up bazel `--jvm_flag`.

2. **AppVersionPinger WARN spam every 10s — cosmetic, ignorable.** Same root cause as #1: appdb has the main commit hash, JVM is v8.0 commit hash. Logs `Detected a version mismatch between the application (875e…) and the Management HTTP Service (4c3e…)`. WARN level, no behavior gate, no impact on probes.

3. **Stale `mongoshTemplate.version` in appdb caused a brief DownloadMongosh failure loop at first agent start.** OM Backup project's automation config had `mongoshTemplate.version="2.6.0"` (carried over from main era), Topology Visualizer project had `"2.8.1"` (updated). Once v8.0 OM republished its config the value moved to `2.6.0` everywhere (v8.0's `conf-hosted.properties` `mongosh.version=2.6.0`). The download itself was blocked by macOS Gatekeeper killing the unsigned binary (`signal: killed`); after a couple of retries the download landed and the symlink check passed. Not blocking — but if you're on an Apple Silicon Mac and see early `DownloadMongosh` errors, ride them out for a minute before investigating.

4. **Agent config `local.config` must reference the correct project.** The 4 cherry-picked configs from `prakhar.dhama/om-backup-local` point at the "Topology Visualizer" project (`6a03286f…`); for "OM Backup" PoC use `mmsGroupId=69ef3ca159819e73bb7f8552` + the matching apiKey. The OM UI silently shows "no agent" / red status if you view the project the agent isn't reporting to — that *is* the bug if anyone tries to run the PoC fresh and sees nothing.

5. **`BounceStopIfUpWithForce` instead of `BounceStopIfUpWithForceKill`.** The v8.0 agent's restore step uses `BounceStopIfUpWithForce` (no `Kill` suffix) — a renaming from older main builds. Worth noting if you're grep-comparing logs across branches.

6. **OM Backup Phase 1 changed the post-restore snapshot behavior.** `RestorationModeSvc.enqueuePreExitSnapshots` (PR #555) queues on-demand snapshots for every RS + sharded cluster in the group right before exiting restoration mode. Observed in Run 1: poRepSet got one auto-snapshot at 14:07:06Z (~1 min after exit) and a second at 14:10:03Z (likely the 15-min scheduled), both complete with 52 fileIds. The two-shard cluster `poShardClust` got per-shard + config-server snapshots a few minutes later. This is **new behavior on v8.0** that didn't exist pre-Phase-1; if you're comparing snapshot inventories to a pre-backport baseline, expect 2× the cadence in the 5-min window after any restoration-mode exit.
